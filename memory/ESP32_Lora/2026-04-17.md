# 2026-04-17 - Sherry-Lora Decentralized Logic

## Project Context
- **Project:** Sherry-Lora (LoRa Water Pump Control)
- **Architecture:** 1 Gateway (Blynk + LoRa Master), 7 Slaves (LoRa + Independent RTC).
- **Core Problem:** High risk of communication failure during multi-hour runs.
- **Hardware Sync:** All slaves are equipped with **DS3231 RTC** modules for high precision.

## Decisions & Logic (Papa's "Staggered Overlap" Proposal)
- **Goal:** Minimize LoRa traffic while ensuring all nodes sync correctly and operate autonomously.
- **Overlap Logic:** 1-minute overlap between sequential relays (similar to SherryOne).
- **Example Calculation (09:30 Start, 5 min Duration):**
    - **B2 (Main Pump):** 09:30 to 10:51 (Total duration for the entire sequence)
    - **B3_R0:** 09:30 to 09:35 (5 min)
    - **B3_R1:** 09:34 to 09:39 (5 min, starts 1 min before R0 ends)
    - **B3_R2:** 09:38 to 09:43
    - **B3_R3:** 09:42 to 09:47
    - **B4_R0:** 09:46 to 09:51
    - ...and so on.

## Workflow (Period 1 & 2)
1. Papa sets **Period 1** and **Period 2** in Blynk.
2. Gateway calculates the specific **Start/Finish** window for EVERY relay across all boards for both periods.
3. Gateway sends these windows to each Slave via LoRa.
4. Each Slave stores these windows in its local **Non-Volatile Memory (Preferences)**.
5. Slaves compare their local **DS3231** time against stored windows to toggle relays.
